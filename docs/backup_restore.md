# バックアップ・復元 手順書

対象は Git に入れていない開発データ（DB / 実設定 / 認証情報 / ローカル専用 /
業務データ）。一覧と検証結果は [git_external_data_inventory.md](git_external_data_inventory.md)。

## バックアップ（定期実行）

1. `development-management\scripts\BACKUP_DEV_DATA_CLICK_ME.cmd` をダブルクリックする。
   - 出力先: `%USERPROFILE%\DevDataBackups\devdata-<日時>\`
   - `E:` 外付けHDDがあれば `E:\DevDataBackups\` にも同じものが作られる。
   - 読み取り専用。アプリを閉じていなくても実行できる（SQLite はオンラインバックアップ）。
2. 週1回を目安に実行する。少なくとも、俺伝や在庫突合で大きな入力・設定変更をした日は実行する。
3. **出力を Git に入れない。** 実際の認証情報・業務データを含む。
4. 可能なら出力を USB メモリ等の**オフライン媒体**にもコピーする（ディスク故障・暗号化被害対策）。

出力の中身:

- `MANIFEST.txt` … 各ファイルのサイズ・SHA-256・DB の integrity_check 結果
- `RESTORE.txt` … どのファイルをどこへ戻すかの対応表

## 復元

**復元前に、現在のファイルを必ず別名で退避してから行う。** 上書きしたら戻せない。

1. どの時点のバックアップを使うか決める（`devdata-<日時>` フォルダ）。
2. `RESTORE.txt` を開き、対象ファイルの復元先を確認する。
3. 復元先の現物を `～.bak` 等へリネームして退避する。
4. バックアップ内のファイルを復元先へコピーする。
   - DB（`*.sqlite3`）はファイルをそのまま置けばよい（完全なDB）。
   - JSON / 設定ファイルも上書きコピーでよい。
5. 対象アプリを起動し、`/health`・主要画面・件数を確認する。
6. 問題なければ退避した `～.bak` を削除する。問題があれば `～.bak` に戻す。

### SQLite の破損時

- バックアップの `MANIFEST.txt` に `integrity_check(...): ok` とある版を使う。
- 破損した現物は消さずに `～.corrupt` 等で保管する（部分救出の可能性）。

## 新 PC での復旧（認証まわり）

- `gh`（GitHub CLI）: トークンはバックアップしていない。新PCで
  `gh auth login` を実行し、ブラウザ認証する。必要スコープ: `repo`, `workflow`, `read:org`, `gist`。
- 俺伝 / 在庫突合の各アプリ内「ログイン情報設定」等: `credentials.json` /
  `google_capture.json` を復元すれば再入力不要。復元しない場合はアプリの設定画面から手入力。

## 対象外（このバックアップに含めないもの）

- `.venv` / `__pycache__` / ビルド出力 … `RUN_DEV.cmd` で再生成できる。
- `ChromeAutomation\` … ブラウザプロファイルのキャッシュ。再生成される。
- 共有配布フォルダ・俺伝HDDの業務データ … 配布先側の運用。別途復元検証すること。
